Objectives
  • Provide a secure, isolated sandbox for executing untrusted user-submitted code.
  • Achieve sub-100 ms container startup using pre-warmed Docker container pools.
  • Support 10 programming languages (Python, C, C++, Java, Go, Rust, Ruby, PHP, JS, TS).
  • Enforce strict resource limits (CPU, memory, PID, I/O) via Linux cgroups to block runaway processes.
  • Apply seccomp-BPF syscall filtering — only a safe allowlist of syscalls permitted per container.
  • Deploy without kernel modifications — portable on any standard Linux system.
  • Provide an online judge portal with timed sessions, test cases, and automatic scoring.
Domain

Container Technology

Uses Docker and Linux primitives (namespaces, cgroups, overlayFS) to create lightweight isolated runtime environments for each code submission.

Operating System Security

Applies seccomp-BPF syscall filtering, AppArmor mandatory access control, and capability dropping — without any kernel modifications.

Online Judge / EdTech

Targets competitive programming platforms, university labs, and technical interview tools as primary use cases.

Full-Stack Web Engineering

Next.js (frontend), Express + TypeScript (backend), PostgreSQL with Prisma ORM, and Monaco Editor for in-browser code editing.

Literature Survey

HClave (IEEE Base Paper)

Proposes a hypervisor-level isolated execution environment using hardware-assisted virtualization (VT-x / AMD-V). Achieves strong isolation but requires kernel-level modifications.

Docker & Namespace Isolation

Linux namespaces (PID, network, mount, UTS, IPC, user) combined with cgroups enable lightweight container-based OS virtualization.

seccomp-BPF Syscall Filtering

Available since Linux 3.5; used in Chrome and Android. Restricting syscalls to an allowlist reduces privilege-escalation attack surface by over 80%.

Existing Judge Platforms

Codeforces (ptrace), Leetcode (proprietary VM), and Judge0 (Docker) show demand for low-latency multi-language execution but lack layered security.

Existing Systems & Drawbacks
Base Paper: HClave — An Isolated Execution Environment for Hypervisor Runtime Security (IEEE)
Requires Kernel Modifications — Demands custom kernel patches and hypervisor changes, making deployment on standard Linux systems impractical.
High Resource Overhead — Full hypervisor-based isolation consumes significantly more CPU and RAM per execution compared to containers.
Complex Deployment — Requires VT-x enabled hardware, custom hypervisor builds, and specialized system administration skills.
Not Suitable for Academic / Small-Scale Use — Proprietary and VM-heavy systems are cost-prohibitive for universities and small platforms.
No Multi-Language Support — Not designed to transparently handle multiple programming languages with different runtimes.
Proposed System
  • Container-based sandboxing — each submission runs in an ephemeral Docker container, destroyed after execution.
  • seccomp-BPF allowlist — only safe syscalls (read, write, open, close, mmap, exit, …) permitted per container.
  • cgroups resource limits — CPU, memory (64–512 MB), PID count (max 64), and I/O tightly capped.
  • Capability dropping — all Linux capabilities removed (--cap-drop=ALL), containers run as non-root.
  • Network isolation — containers start with --network=none, blocking all outbound access.
  • Pre-warm pool — 50 containers kept ready at all times, delivering <100 ms response.
  • No kernel modifications — runs on any standard Linux host via a single docker-compose up.

Frontend Layer

Next.js 14 with Monaco Editor. Real-time output streaming via WebSocket. Admin and Participant dashboards.

Backend API Layer

Express.js + TypeScript. JWT auth, rate limiting, security validation, and Docker container orchestration with a pre-warm pool of 50.

Database Layer

PostgreSQL running in Docker. Prisma ORM for type-safe queries. Stores users, sessions, questions, test cases, and submissions.

Modules

1. Authentication Module

JWT-based login/register with bcrypt hashing. Role-based access control (Admin / Participant).

2. Container Orchestrator

Maintains a pre-warmed pool of 50 sandbox containers. Assigns and destroys containers per execution.

3. Security Layer

seccomp-BPF allowlist, capability dropping, read-only FS, user namespace remapping, and network isolation.

4. Code Execution Engine

Accepts code + language + stdin. Streams stdout/stderr via WebSocket. Enforces timeouts and memory caps.

5. Admin Portal

Create questions with test cases, set up timed sessions with access codes, monitor participant submissions.

6. Participant Portal

Join sessions via access code, solve problems in browser IDE, submit for automatic test-case validation and scoring.
